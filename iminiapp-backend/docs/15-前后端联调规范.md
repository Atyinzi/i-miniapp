# i某小程序 - 前后端联调规范

版本：v1.0（2026-08-03）
适用范围：当前 Spring Boot 后端与微信小程序、管理端页面的联调。

## 1. 联调前置条件

1. 启动 MySQL 8、Redis 7 和 `IminiappBackendApplication`。
2. 后端默认地址为 `http://localhost:8080`；先请求 `GET /api/v1/app/system/health`，响应 `code` 为 `SUCCESS` 才开始联调。
3. IDEA HTTP Client 使用 `http/api-examples.http`，不要使用含本机令牌的 `http/local-api.http`。
4. 数据库迁移由 Flyway 自动执行；禁止手工修改已执行的迁移脚本或直接修改 `flyway_schema_history`。

## 2. 统一请求与响应约定

所有 JSON 使用 UTF-8，金额字段使用整数分，例如 `8000` 表示 80.00 元。成功响应格式：

```json
{
  "code": "SUCCESS",
  "message": "操作成功",
  "data": {},
  "traceId": "请求追踪编号"
}
```

失败时 `data` 为 `null`。前端应展示 `message`，并在联调问题中同时提供 HTTP 状态、`code` 和 `traceId`。常用错误为：

| HTTP 状态 | 业务码 | 前端处理 |
| --- | --- | --- |
| 400 | `SYSTEM_400_001` | 提示输入或请求参数错误，不自动重试 |
| 401 | `AUTH_401_001` | 清空令牌并重新登录 |
| 403 | `AUTH_403_001` | 提示无权限，不跳转管理功能 |
| 404 | `SYSTEM_404_001` | 提示数据不存在或已下架 |
| 409 | `INVENTORY_409_001`、`ORDER_409_001`、`REFUND_409_001` | 刷新订单、库存或退款状态后再操作 |
| 429 | `SYSTEM_429_001` | 按 `Retry-After` 延迟重试 |

创建订单、支付、设置库存和提交退款申请必须带 `Idempotency-Key` 请求头。前端对同一次用户操作重试时使用同一键；发起新的业务操作时生成新键。不要把令牌、数据库密码或回调密钥写入代码仓库。

## 3. 登录与角色

开发联调使用模拟登录。后端重启后令牌失效，应重新执行以下接口：

| 角色 | 登录接口 | 令牌变量 | 可访问范围 |
| --- | --- | --- | --- |
| 用户 | `POST /api/v1/app/auth/mock-login`，`accountType=USER` | `userToken` | 小程序用户端 `/api/v1/app/**` |
| 管理员 | 同上，`accountType=ADMIN` | `adminToken` | 管理端 `/api/v1/admin/**` |
| 运维 | 同上，`accountType=OPS` | `opsToken` | 运维核销接口 `/api/v1/ops/**` |

所有受保护接口均使用 `Authorization: Bearer <accessToken>`。前端不得仅靠页面隐藏控制权限，后端返回 403 时必须停止请求。

## 4. 已实现接口联调矩阵

| 业务 | 前端接口/关键接口 | 核心验证点 |
| --- | --- | --- |
| 景区浏览 | `GET /api/v1/app/scenic-spots`、`/{id}`、`/{id}/tickets` | 只展示上架景区和票种；按游玩日期展示库存与价格 |
| 下单支付 | `POST /api/v1/app/orders`、`/{id}/mock-pay` | 幂等键重复提交不重复扣库存；支付后生成电子票 |
| 电子票核销 | `GET /orders/{id}/tickets`、`POST /api/v1/admin/verifications/consume` | 二维码一次有效；身份证核验仅限当天实名票 |
| 项目套票 | `GET /scenic-packages/{skuId}`、管理员组件维护接口 | 套票支付后按组件生成多张独立电子票 |
| 退款 | `POST /orders/{id}/refund-applications`、管理员审核、渠道回调 | `PENDING_REVIEW → PROCESSING → SUCCESS/FAILED`；成功后订单退款、票作废、库存归还 |
| 导览 | `GET /scenic-spots/{id}/guides`、`GET /scenic-guides/{id}` | 用户端只看 `ACTIVE` 内容；管理员可维护四类导览 |
| 运营 | `GET /admin/scenic-spots/{id}/operations/summary`、`/verification-records` | 销售、电子票、核销数据按规定日期口径返回 |

完整可执行请求在 `http/api-examples.http`：登录为第 1—4 步，景区票务为第 25—44 步，退款为第 14、45—50 步，导览为第 51—54 步。

## 5. 页面联调顺序

1. 登录页：获取并保存令牌；401 时回到登录页。
2. 景区列表/详情页：查询景区、票种、日期库存；下架或无库存状态不可提交。
3. 下单页：生成 `Idempotency-Key`，提交游客信息；成功后保存 `orderId`。
4. 订单详情页：轮询或主动刷新支付、退款与电子票状态；金额按“分”转“元”显示。
5. 核销页：扫描电子票 `code` 后调用管理员/运维核销接口；成功后禁止重复扫同一票。
6. 管理端：先完成票种、库存、套票组件配置，再让用户端下单；退款审核后等待渠道回调结果。

## 6. 联调问题提交模板

```text
页面/功能：
请求时间：
角色：USER / ADMIN / OPS
请求方法与地址：
请求体（脱敏后）：
HTTP 状态：
响应 code/message/traceId：
预期结果：
实际结果：
截图或日志：
```

前端修改字段、枚举、日期格式、金额单位或接口路径前，必须在联调群/任务中确认，并同步更新接口示例和本文件。后端变更应保持向后兼容；无法兼容时增加新版本接口或明确发布窗口。
