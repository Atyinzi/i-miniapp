# 文旅景区预订模块说明

## 1. 已完成范围

本次完成可独立联调的景区门票最小业务闭环：

1. 景区分页列表与名称、介绍、地址关键词搜索。
2. 景区详情、地址、坐标、客服电话、营业信息查询。
3. 按游玩日期查询票种、当日价格、库存和购票规则。
4. 实名游客校验及敏感信息加密保存、脱敏查询。
5. 创建订单时锁定库存，取消或超时释放库存。
6. 模拟支付后按购票数量签发电子票。
7. 工作人员核销，全部电子票核销后订单完成。
8. 用户提交退款申请，管理员审核后由退款渠道回调确认；成功后电子票作废并恢复库存。
9. 工作人员可扫描电子票二维码，或按身份证号核验当天的实名电子票。
10. 管理员可维护项目套票，支付后按套票组件分别生成可独立核销的电子票。
11. 管理员可按景区和日期范围查询售票、入园和核销记录。

暂未包含景区图文/语音导览、评价、优惠券和真实支付，这些属于后续迭代，不影响当前前后端联调。

## 3. 创建景区订单示例

```json
{
  "items": [
    {
      "skuId": 123,
      "quantity": 1,
      "serviceDate": "2026-07-31",
      "timeSlot": "",
      "businessData": {
        "visitors": [
          {
            "name": "张三",
            "mobile": "13800138000",
            "idType": "ID_CARD",
            "idNo": "150204199001011234"
          }
        ]
      }
    }
  ],
  "remark": "景区门票预订"
}
```

请求必须携带唯一的 `Idempotency-Key`。实名票的 `visitors` 数量必须等于 `quantity`，游玩日期不能早于当天。

## 6. 管理端票务与时段管理

本模块已提供管理员专用接口。管理员先通过模拟登录获取 `adminToken`，再放入 `Authorization: Bearer ...` 请求头。

Web 运营管理端已新增“景区票务运营”入口（`/scenic`），按“门票与限流、导览服务、运营分析”三个工作区组织操作，可直接完成本节及第 8、11 节的后台业务。

支持的 `ticketType` 为：`ADULT`（成人票）、`CHILD`（儿童票）、`PACKAGE`（套票）、`SERVICE`（服务票）和 `OTHER`（其他票）。票种规则可配置适用人群、使用规则、退款规则、入园须知、有效天数、单次限购、实名购票和身份证要求。

时段库存接口需携带唯一的 `Idempotency-Key`。当一个时段已被预订时，系统会保存已预订数量；运营人员提高总容量时只增加可售名额，尝试把总容量调低到已预订数量以下会被拒绝，避免超卖或误伤已付款订单。

`http/api-examples.http` 的第32—34步提供了可直接运行的管理员联调示例。

## 7. 项目套票规则

项目套票使用独立的 `PACKAGE` 类型景区票种表示：它有自己的售价、上架状态、预约库存、限流和下单记录；它不是前端临时拼接的价格展示。创建套票后，管理员必须配置 **2—10 个**有效的普通景区票组件；组件不能重复、数量为 1—10，且不允许把另一个套票作为组件，避免循环和嵌套核销。

用户只购买套票 SKU。下单时系统仅锁定套票自身的预约库存，并将当时的组件 SKU、名称、景区名称和数量快照写入订单。以后运营人员调整套票组成，不会改变已经购买的订单。支付成功后，系统不签发一张“总套票”；而是按组件数量分别签发电子票，每张电子票都有自己的二维码，可由不同游客、在不同检票口分别核销。全部组件电子票核销完成后，订单才会变为完成。

套票组件的库存不随下单自动扣减，原因是一个组件可能被多个产品共享，实际接待能力往往还受闸机、场次和人工服务限制。当前版本以套票库存作为唯一交易库存，运营人员必须按最紧缺组件的可接待能力设置套票库存；例如两个项目各能接待 50 人，则双人联票最多设置为 50 份。这项规则避免多重锁库造成的库存不一致，后续如需要跨项目实时共享库存，可在库存域增加“组合库存池”而不改变订单和电子票模型。

接口联调按 `http/api-examples.http` 第36—42步执行：创建套票、配置两个组件、设置套票库存、查询详情、下单、支付、查看组件电子票。第42步应返回组件名称不同的多张 `UNUSED` 电子票；核销其中一张时订单仍为已支付，全部核销后订单完成。

## 8. 景区运营数据与核销记录

管理员可以按景区和最多31天的日期范围查询运营概览：

- `GET /api/v1/admin/scenic-spots/{scenicSpotId}/operations/summary?startDate=2026-07-31&endDate=2026-07-31`
- `GET /api/v1/admin/scenic-spots/{scenicSpotId}/operations/verification-records?startDate=2026-07-31&endDate=2026-07-31&page=1&pageSize=20`

概览中的 `paidOrderCount`、`soldTicketCount` 和 `salesAmountCent` 按所选**游玩日期**统计已支付订单；`issuedTicketCount` 是该日期已签发且未作废的实际电子票数，`verifiedTicketCount` 是其中已核销数，`verificationRate` 为两者的百分比。这样套票按“套票份数”统计销售，同时按实际组件电子票统计入园，避免一份包含多项目的套票把核销率计算为超过100%。

核销记录按实际 `verifiedAt` 时间筛选，只返回已核销的电子票、订单号、票种/景区名称、核销员和核销方式（二维码或身份证），不返回核销码、游客姓名、手机号或身份证号。`http/api-examples.http` 的第43—44步可直接验证该能力。

## 9. 身份证核验入园

实名票支付后，系统会将每张电子票绑定到对应入园人。管理员或运维人员可调用
`POST /api/v1/admin/verifications/consume-by-id-card`，提交身份证号完成当天入园核验。

身份证号只在请求处理期间用于计算加密检索摘要；数据库不新增身份证明文或明文审计日志。每位实名游客只能核销其绑定的一张未使用电子票，重复核验会被拒绝。实际身份证读卡器可在后续接入时，将读取到的号码提交到同一接口。

## 10. 退款申请与审核

景区门票退款使用 `PENDING_REVIEW → PROCESSING → SUCCESS/FAILED` 状态机。用户只能为本人已支付且未核销的景区门票订单申请整单退款；申请阶段不归还库存、不作废电子票。管理员通过后，订单进入 `REFUNDING`，禁止继续核销；退款渠道成功回调后，系统才把订单改为 `REFUNDED`、作废未使用电子票并原子归还库存。渠道失败时退款变为 `FAILED`，订单恢复审核前状态，电子票和库存不变。

管理员可通过 `/api/v1/admin/refund-applications` 分页查询，调用 `/{refundId}/approve` 或 `/{refundId}/reject` 审核。用户通过 `/api/v1/app/refund-applications` 查询自己的申请和进度。每次状态变化写入 `bf_refund_status_log`，订单时间线可展示申请、审核与渠道结果。旧 `/mock-refund` 端点默认禁用，仅在显式启用 `legacy-mock-refund` Profile 时存在。

本地联调执行 `http/api-examples.http` 第14、45—50步。正式接入微信支付退款时，应把模拟渠道调用替换成微信支付 V3 退款接口，并在回调入口增加微信平台证书验签；订单、电子票、库存和退款状态机无需重写。

## 11. 景区导览内容

管理端可维护 `MAP`（地图）、`ATTRACTION`（景点介绍）、`AUDIO`（语音导览）和 `STRATEGY`（游玩攻略）四类内容，设置标题、摘要、封面、媒体地址、正文、时长、排序及发布状态。用户端只返回 `ACTIVE` 内容，草稿和已下架内容仅管理员可见。

用户接口为 `/api/v1/app/scenic-spots/{scenicSpotId}/guides` 和 `/api/v1/app/scenic-guides/{guideId}`；管理接口为 `/api/v1/admin/scenic-spots/{scenicSpotId}/guides` 与 `/api/v1/admin/scenic-guides/{guideId}`。第51—54步提供直接联调示例。开发数据中的图文与音频路径仅为占位，正式发布前必须由运营方提供有版权的素材和可访问对象存储地址。
