# 车辆内部员工与司机身份接入说明

## 一、身份设计

微信登录账号仍然统一存放在 `bf_user`。员工和司机不是互斥的登录账号类型，而是同一微信用户可以拥有的业务身份：

- `bf_employee` 保存内部员工、部门、工号、在职状态和微信用户绑定关系；
- `bf_driver` 保存司机档案和微信用户绑定关系；
- `bf_user_role` 分别授予 `EMPLOYEE`、`DRIVER` 角色；
- 姓名、手机号采用加密字段存储，手机号额外保存不可逆检索摘要；
- 管理员、运维人员继续使用独立的管理端账号和权限体系。

这样既能区分内部员工、司机和社会用户，又允许一名员工同时具有司机身份。

## 二、内部用车流程

1. 管理员维护部门和员工档案。
2. 管理员直接绑定微信用户，或员工在微信手机号授权后使用工号自助绑定。
3. 只有员工和所属部门均为 `ACTIVE` 时才能提交内部用车申请。
4. 员工可查询自己的申请，并可取消仍处于 `PENDING_APPROVAL` 的申请。
5. 管理员审核、派车；司机在司机工作台接单、出发、上报位置和完成任务。

内部用车不走在线支付和押金流程，订单类型为 `VEHICLE_INTERNAL`，业务模式为 `INTERNAL`。

## 三、社会租赁流程

社会用户不需要员工身份，可从小程序社会租赁入口选车、报价、下单和支付。订单类型为 `VEHICLE_RENTAL`，业务模式为 `SOCIAL_RENTAL`。司机完成社会租赁任务时，后端会进入还车结算流程，不能直接把订单标记为完成，从而保留补款、押金退还和车辆状态处理。

## 四、司机工作台

司机工作台统一读取当前司机名下任务，响应中的 `businessMode` 用于前端区分：

- `INTERNAL`：内部员工用车；
- `SOCIAL_RENTAL`：社会车辆租赁。

司机只能操作分配给自己的派车单。解绑司机账号前，系统会检查是否还有待接单、已接单或进行中的任务。

## 五、联调顺序

1. 运行 `V67__add_vehicle_employee_identity.sql` 数据库迁移并启动后端。
2. 使用管理端登录令牌创建部门和员工档案。
3. 使用真实微信登录用户完成手机号授权和员工绑定。
4. 按 `http/vehicle-identity-api.http` 测试内部申请、取消、派车和司机履约。
5. 使用社会租赁订单再次验证司机完成任务后进入还车结算。

生产环境不得启用模拟登录；接口测试必须使用微信登录令牌或管理员登录令牌。
